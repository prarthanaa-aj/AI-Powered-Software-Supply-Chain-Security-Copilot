# Risk Labeling Plan and Data Limits

## Why no model result is reported yet

The current learner's target is a human risk label for a package finding, while its inputs include CVSS, exploit evidence, directness, dependency depth, and vulnerability count. This repository contains no independently labeled cases. A model trained on labels generated by the current heuristic would merely imitate that rule, so no such dataset is created.

## Candidate sources and their limits

- [CISA Known Exploited Vulnerabilities Catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) is an authoritative source for vulnerabilities known to have been exploited. Catalog membership can support a positive label for a narrowly defined “known exploited” target. A missing CVE from the catalog is not proof that it was never exploited, so it is not a defensible negative label for that target.
- [FIRST EPSS methodology](https://www.first.org/epss/how-it-works) describes a probability estimate for exploitation in the next 30 days. EPSS is a model output, not independent ground truth for this project's broader remediation-risk label. Copying EPSS into labels would train a model to imitate EPSS.

Neither source alone supplies the package-level directness, dependency path, and per-project context expected by the existing feature schema. Joining CVEs to package advisories and project manifests would need a documented mapping, time cutoff, deduplication rule, and independent analyst rubric. Therefore, these sources are candidate evidence, not a ready-to-train dataset.

## Required annotation protocol

Before collecting rows, define exactly what label 1 means, for example “analyst recommends remediation within a specified window under the recorded deployment context.” Have two reviewers label cases independently while blinded to the heuristic/model score; adjudicate disagreements and preserve the rationale and evidence. Each row must retain `group_id` so related findings from the same project/advisory cannot cross the validation split. Record source IDs and observation dates in a separate protected provenance file; do not include secrets or private project identifiers in the model CSV.

The current CSV template is a schema only. Validation remains `insufficient_data` until both classes and enough independent groups are represented. Even a passing holdout on collected examples would not establish external validity; a later time-based or external-project evaluation would still be needed before model promotion.
